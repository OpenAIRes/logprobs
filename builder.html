Builder — growing the database

Always expands the best candidate not yet tried (best-first / Dijkstra). Every response gives 20 alternatives at every position, so each candidate's logprob is known before any call — the frontier can be ordered for free. The database therefore grows in exactly the order it will be read in.

New calls per run is the budget for one press of Run, not an absolute cap — each further press adds another N. Step is not budgeted.
Proven top-K: if the best frontier candidate has sum S, then every discovered prefix with sum > S can no longer be overtaken by anything — its position is final. That is exactly the property that makes Dijkstra correct.
Unseen ceiling: the API returns only 20 alternatives per position out of a ~100,000 token vocabulary, so every expanded node also has children nobody ever saw and which are in no frontier. They are bounded, though: outside the top 20 a token's logprob is ≤ the 20th, so the whole unseen subtree under node N has sum ≤ N.sum + min(top20). The largest such bound is a hard ceiling: below it nothing can be proven from top-20 data, however many calls are made. Proven top-K therefore follows whichever limit is worse; when the ceiling starts to bind, it is marked ⚑.
