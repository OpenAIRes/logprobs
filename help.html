What every view and every option means, and the standard term for it where one exists. Everything here reads one database: the log of calls actually made to gpt-3.5-turbo-instruct at temperature 0.

The data

One call to the legacy /v1/completions endpoint with logprobs: 20 returns, for every token it generated, that token's log-probability and the 20 highest-ranked alternatives at that position. All calls here use temperature: 0, so the token returned at each position is the argmax — the most probable one — and every alternative is by definition no more probable than it.

That is what makes most of this cheap. A single call tells you the cost of every one-token deviation from the string it produced. Only following a deviation — seeing what the model writes after it — needs another call.

top_logprobs is capped at 20 for gpt-3.5-turbo-instruct and at 5 for davinci-002 and babbage-002. A model showing 5 alternatives instead of 20 is the endpoint's limit, not a bug here.

Views

Greedy path greedy decoding, temperature 0
What the model actually produces from a prompt: at every position the single most probable next token. This is a path, not a ranking — there is nothing to sort, because at each step there is exactly one argmax. It is the default view because it answers the default question: what does this model say to this prompt.

Records are chained: each hop's generated text is appended to the prompt and the store asked again, so a path can run past any single call. From the empty prompt that is one record and 4096 tokens; from I have it is two records and 40.

The temperature-0 premise is checked, not assumed. Every generated token should be the argmax of its own top_logprobs, and the view reports whether that held. Across all 8492 records it holds for 179171 of 179171 tokens — but a −9999 sentinel is exactly the shape a violation would take, so the check is worth its cost.

A path that ends on finish_reason: length was cut by max_tokens and could go further; one that ends on stop is the whole string the model wanted to write.

Greedy path + next best one-token departures, ranked
Rank 1 is the greedy path. Every other row is that path with one token changed, then greedy again — so "second best by the greedy criterion" is the cheapest departure. The cost of every departure is already in top_logprobs, so the ranking is free; only having a continuation on record is not, and the view says how many departures would need a call.

The ordering is not one thing, and this is where it gets interesting. By deviation cost, #2 is position 4, 9→8, giving up 0.0352 nats and landing on the 2018 FIFA World Cup with Σ −16.25. By resulting Σ logprob, #1 is position 0, →﻿using, which costs 1.78 nats — fifty times more — and reaches Σ −6.58.

The greedy path scores −15.41 over those same 21 tokens. So one deliberately expensive first step ends up about 8.8 nats — some 6800× — more probable than greedy decoding. That is the textbook fact that greedy is locally optimal and not MAP, and on this data the gap is not subtle.

Completions whole sequences
One entry per recorded call: the whole string that call produced, prompt included. Ranked by cumulative logprob, descending. These strings are not all the same length — the generated part is max_tokens, but the prompt grows with the position a deviation was made at, so a position-0 branch runs about 21 tokens and a position-19 branch about 40. Ranking by a sum therefore favours the shorter ones, which is why mean logprob sits in the next column.
Prefixes — best-first n-best list, uniform-cost search
Every prefix in the token trie, in exact rank order. Because every logprob is ≤ 0, extending a prefix can never raise its sum, so pulling prefixes off a max-heap yields them in provably correct order — this is Dijkstra's algorithm, or uniform-cost search, over the trie. A prefix is a path, not a call: several calls contribute to one, and a prefix has no single record behind it.
Alternatives grid per-position top-k
For one base completion, every position as a row, and in each row all 20 alternatives the model offered there. The one it actually chose is framed. This is the shape the sweep data really has; a ranked list flattens it and loses exactly the thing worth seeing — how far behind the rejected tokens sat.
Cheapest-deviation walk greedy hill-climbing over single-token edits
Repeatedly: find the single-token deviation that costs the fewest nats, apply it, regenerate the continuation. Which deviation is cheapest is free to work out — it is already in the data — so a walk of N strings needs N calls, not N×400.

It produces a path, not a ranking. The top of the Completions list is the most probable strings; a walk shows how the output drifts when you keep paying as little as possible for each departure. Those are different questions.

Two guards are not optional. After deviating at position i, the token sitting there is no longer the argmax, so the cheapest move at that position is to put the original back — at negative cost. It would win every time and the walk would oscillate on step one, so a deviated position is frozen. And deviating at an earlier position unfreezes the later ones, which makes a longer cycle reachable, so strings already walked are never revisited.

Options

ranked by the sort key
Only the Completions view offers this. Prefixes come off a sum-ordered heap, so there the ranking is the search order; reordering an n-best list by something else would give "the best mean among the n best by sum", which reads like an answer and is not one.

Σ logprob favours short strings, because every extra token can only subtract. perplexity is length-independent. length puts the longest first. In the greedy view there is also deviation cost, and it is the default there, because giving up the fewest nats at the point of departure is precisely what makes a sibling the second best by the greedy criterion.

Perplexity and mean logprob are the same ordering, not two criteria. Perplexity is e−mean, a strictly monotone transform, so ascending perplexity is descending mean rank for rank — verified across all 363 greedy siblings. Only perplexity is offered, because it is the standard way to report the per-token measure; ?sort=mean still works and means the same thing.

None of these is how you ask for the string a prompt produces — that is the Greedy path view. Sorting completions by length happens to surface the greedy string on this data, and would stop doing so the moment a longer string existed that was not the greedy one. Ranking answers "which strings are probable"; greedy decoding answers "what does the model say".

The sort is applied before the results cap, which matters more than it sounds: the 4096-token unconditional root has the best mean logprob of all 8128 entries (−0.0127) and sits at rank 7786 by Σ logprob. Sorting after a cap of 5000 would have hidden the very entry being asked for.

results
How many entries the ranking is computed and shown for. Set it to 1 and you are asking for a single string, so it opens in the token browser instead of as a one-row list: every token with its top-20 alternatives, and a click follows one of them.

Above 1 it is a list. The cap is 2000 because each entry carries per-token detail — 600 completions are about 7.5 MB, 5000 about 72 MB.

starts with prefix filter
Keeps only strings beginning with this text. Leading whitespace is ignored on both sides, since nearly every string here starts with a newline. The filter is applied before the results cap, on the server, so matches far down the ranking still come through — searching only the top 200 would miss most of them.
base completion
Which recorded call a grid or a walk starts from. The list is built from the store, so a newly swept base appears on its own. The number is how many calls that base has around it.
steps
How many walk steps to attempt. The walk stops early when the next regeneration is not in the database, and says which prompt it would need — it never calls the API on its own.
forward only
Restricts each step to positions at or after the last deviation, so every string extends the previous one instead of replacing part of it. It costs more per step, visibly: from the porchlight base, a free walk goes back to position 1 for 0.1079, while forward-only must go to position 17 for 0.1252.
model
Which model's records to use. Data from different models is never mixed: a record only answers a request for the same model it was asked of. This matters because the alternative count differs — 20 versus 5 — and because a davinci-002 continuation of a gpt-3.5-turbo-instruct prefix would be a different distribution presented as the same one.

Scope — how a string ends

Every ranked row is a string, but not every string ends for the same reason, and the reason decides whether two rows can be compared at all. The scope checkboxes select which endings fall into the list.

Only stop is a finished string. The other two are both prefixes of something longer, and they differ only in whose cut it was — our max_tokens, or our enumeration of the trie. Nothing about the string itself distinguishes them.

stop EOS-terminated, complete generation
The model emitted <|endoftext|> and the call returned finish_reason: "stop". The string is finished, so its Σ logprob is a final quantity. 219 of 8492 records — 2.6%.
length length-truncated — a prefix
max_tokens ran out mid-string. Σ logprob is a partial sum that would only get more negative if the string continued. 8273 of 8492 records — 97.4%, so nearly the whole corpus. This always means the ceiling and nothing else: of the 8232 distinct length-ended paths, none stopped before its max_tokens.
open partial hypothesis — also a prefix
Nothing recorded ends here at all; the string stops where the trie enumeration stopped. Only a row in the Prefixes view can be this — a completion and a greedy sibling are both recorded calls and always carry the API's verdict, so the box is disabled in those views rather than silently returning nothing. Every one of the 168,669 open nodes is an interior node with the trie continuing below it: the trie only ever contains tokens some call actually generated, so there are no open leaves.

the bar

Three icon buttons, and that is the whole visible strip — there is no page navigation above it any more. It held one link most of the time and a record count that the meta block below already reported, so its links moved into the settings panel: start over, help, and the full settings page.

The three buttons:

palette glyphcolour — shade every token by the probability the model gave it. Off by default.
sun or moonpalette — light or dark. The glyph shows the one you are in; clicking gives the other.
gearsettings — everything that decides which strings are on screen: view, results, ranked by, how complete, prompt, starts with, model, base, steps, extend, recovered tokens, endings.

The split is deliberate. The strip carries what is about reading what is already there; the panel carries decisions. The count on the right is neither — it says what you are looking at, not what to do about it — and neither is the status line beside it, which is where a page reports its own progress instead of keeping a strip of its own.

The palette is the one setting kept out of the address. It is about the person reading, not about what is on screen, so a shared link should not force a stranger into someone else's. It follows the machine on a first visit and is explicit from then on.

colour

Off by default. Ticked, every token is shaded by the probability the model gave it at that position — green above 0.6, amber above 0.15, red below, with the shade tracking the probability so a near-certain token reads solid and an unlikely one as a faint wash. The same scale on both pages: it used to exist only in the lists view, so one token was a plain word in the browser and coloured in the table.

A prompt token stays uncoloured. Nothing predicted it, so it has no probability to show.

The colour rides on a custom property per token and the box toggles one class, so turning it on and off costs no request and no re-render — it is display, not a different query.

prefix → complete — one axis, three nested stops

A three-position stepper — a slider only in how it is drawn; the standard name for a control with a few named, ordered choices is a segmented control. It is deliberately narrow and ticked, because three positions spread over a wide track read as a continuum, which is the one thing this is not. Its stops are nested: each is a subset of the stop to its left, so stepping right only ever narrows.

The middle stop carries no visible name — there is no good short one — so it shows only its count, names itself on hover, and spells itself out in the line under the slider once selected.

The stepper drives the boxes; it does not replace them. They live behind set the endings by hand because the stepper already reaches the three points worth reaching. They can still say things the axis has no stop for — continues on its own, say, or open alone — and then the stepper dims and reads combination rather than pointing at a stop it does not mean.

Whether the database holds anything past this string. A separate axis from how the string ended, and the two cross — which is the whole reason it needs its own boxes:

An open node has a continuation by construction. But 494 length paths do too: the call stopped at max_tokens, and then a later call took that whole text as its prompt and carried on. So “don't list prefixes we have a continuation for” is not unticking open — that still leaves those 494. Untick continues instead.

A row the database continues past is marked ⋯ next to its ending. Both sides are populous — 168,734 against 7,915 reachable — which is why this is a pair and recovered below is a single box.

Not the same as extend. Extend does not filter; it moves each row to its dead end. Twenty rows with extend on are twenty extended prefixes that happen to end at a dead end; twenty rows with only dead end ticked are the twenty best dead ends.

recovered tokens

A token gets into the trie only if some call generated it. Its log-probability, though, may come from either place: the call that generated it (chosen, 169,208 nodes) or another call's top_logprobs listing it as an alternative (alt, 7,870). Untick recovered and only the first kind may appear on a path.

It is not a mild filter. A path must qualify all the way down, and the root has one chosen child out of 21 — so the reachable prefixes go from 176,649 to 4,174, a 97.6% cut, not the 7,870 the node count suggests. The label carries the two numbers for that reason.

Only the Prefixes view offers it: it is the only view that walks token by token. There is no matching “only recovered” option, because a path every one of whose tokens is an alternative reaches just 416 nodes — a pair of boxes would imply a symmetry that is not there.

How many there are

There is no box for “all prefixes”, and adding one would be a lie: the three endings ticked already means all of them, and what stops you is the results cap. The list says the fraction instead — both the start page, before you open anything, and the header of the list itself.

The 451 are not a setting anyone chose. build_trie fills a node's log-probability from a generated token or from its parent's top_logprobs, so a sweep's deviated token stays unscored whenever the position it deviates at was only ever a prompt position — that node has no alternatives table of its own. 22 such nodes block 429 below them, and past an unscored node a running sum no longer counts from the root, so the search may not cross one. Those 22 are exactly the difference between the 8,431 recorded endpoints and the 8,409 a search can reach.

extend

A separate axis from the three above, not a fourth kind of ending. A prefix row normally stops where the enumeration stopped, even though the database holds continuations of it. Tick extend and each row is followed on from there — taking the model's own argmax at every step — to the furthest end on record.

The rule is the node's top_logprobs, the distribution the API actually reported for the next token, not simply the highest-scoring child in the trie. The two agree at 168,979 of 168,992 nodes. Where they disagree the child belongs to a different context: the trie is keyed by token path, and a path reached as someone's prompt is not the same context as the same path generated from an empty prompt, because an empty prompt is served with an implicit <|endoftext|> that the trie does not model. Exactly one node — (" ",) — is reached both ways.

The ranking still belongs to the prefix. Extending changes the score, and over the default top 200 ranking by the extended sum would reorder 11,325 of 19,900 pairs. So the row keeps its own Σ logprob as the ranked value and the extension's total is shown beneath it, after an arrow. A list ordered by one number while showing another would be worse than no feature.

Rows collapse. 200 prefixes extend onto 93 distinct strings, one of them reached 22 times — every prefix of the same continuation lands on it. Rows that repeat an earlier row's string are marked =n with that row's rank rather than hidden, because 200 rows showing 93 answers should look like it. The top three completions all extend to the same string, at Σ −19.7152.

An extension always lands on a real end: 188 length and 12 stop over the default 200, never open, because the trie has no open leaves. Per-token detail is capped at 400 tokens per row — the totals always cover the whole extension — since one row alone adds 4095.

Scope applies to every view that produces a list of strings: Completions, Prefixes, and the greedy path with its siblings. It does not apply to the greedy path on its own — with one result there is exactly one string and nothing to select from. Of the 363 greedy siblings, 359 end on length and 4 on EOS; ticking only stop is how you ask which single-token departures lead somewhere the model actually finishes. The cheapest that does costs 1.0327.

Why it is a control and not just a label. Σ logprob over a one-token prefix beats Σ over anything longer, so a ranking that mixes the three is dominated by the shortest rows: the default Prefixes top 200 is 195 open, 3 length, 2 stop, median length 3 tokens. Untick open and the same ranking lists the same strings the Completions view does.

The filter is applied inside the search, not to its output. Filtering the top 200 afterwards would answer “the best finished strings among the top 200 by Σ”, which is a different question. Searching for stop alone walks 176,649 trie nodes to find all 197 of them; if a search ever hits its step budget, the page says the list may be incomplete.

How close a length string came to finishing is not knowable. top_logprobs gives the distribution before each generated token, so the distribution after the last one — the only place EOS could have shown up — is never reported. A truncated string could have been one token from the end or a thousand; the data does not say.

EOS is never itself a listed token — it is stripped from logprobs.tokens, so the one position that would prove termination is the one the API does not report. It does appear in top_logprobs at 40,689 of 179,171 positions (22.7%), where it was ranked but not chosen; its highest log-probability anywhere in this data is −0.9832.

Scores

Σ logprob cumulative / sequence log-probability
The sum of the per-token log-probabilities, i.e. log P(sequence). Always ≤ 0; closer to 0 is more probable. Comparable only between strings of the same length and the same kind of ending — over a prefix it is a partial sum, over an EOS-terminated string it is final. See Scope.
mean logprob per-token average
Σ logprob divided by the number of tokens. Length-independent, so it is the one to use when the strings differ in length.
perplexity
e−mean logprob. A monotone transform of mean logprob, so it never changes the ordering — it is the same information on a scale where 1 means perfectly predicted and larger means less so.
Σ logprob = Σ log P(tokenᵢ) · mean = Σ / n · perplexity = e^(−mean)
which of these is “what the model would say”?
Σ logprob, not perplexity. Sampling at temperature 1 produces a string with probability exactly eΣ logprob, so the string generated most often is the one with the highest Σ — that is MAP decoding. Perplexity is Σ divided by the length, so it measures predictability per token and rewards long, predictable strings, which are the least likely to come out. Over the 197 completed strings we have: best by Σ is 5 tokens at P = 6.6×10−4, best by perplexity is 767 tokens at P = 2.0×10−78 — 3×1074 times less likely, and 194th of 197 by Σ. The greedy path is the extreme case: perplexity 1.0128, near-perfect per token, and P = 2.6×10−23.
Two things this rests on. “Most often” only means anything above temperature 0 — at 0 the model is deterministic and its one string comes out every time. And MAP is only well posed over completed strings: every factor in the product is ≤ 1, so Σ only falls as a string grows, and over prefixes too the most probable is trivially the empty one. That is the complete stop on the stepper.
cost of a deviation nats
logprob(chosen) − logprob(alternative) at that position. Since the chosen token is the argmax at temperature 0, this is ≥ 0. A cost of 0.0352 means giving up about 3.5% of relative probability on that one token.

A sampled token can come back with −9999 when it fell outside top_logprobs even at 20. That is a sentinel, not a log-probability; summing it produced a confident-looking p = 0, so such strings are reported as unscored rather than scored wrongly.

Extending a view

Every view can be pushed further, and what "further" means depends on the view. Nothing extends on its own — each of these costs real API calls and is started explicitly.

ViewExtending it meansWhere
Completions / Prefixes Expand the best prefix not yet tried, so the database grows in the same order the list is read in Builder, in the browser
Alternatives grid Sweep a base: follow every alternative at every position — 20 × 20 calls for one base sweep_alternatives.py
Cheapest-deviation walk Pay for the next regeneration the walk stopped at — one call per step sweep_alternatives.py, or step it in the token browser
Greedy path Pay for the continuation past where the records stop — the view names the prompt it would need Token browser, or stream_logprobs2.py
Single string Click a token to follow an alternative; the call happens only if no record answers it Token browser

The Builder expands the best untried candidate first (best-first, same ordering as the Prefixes view), so the database grows in the order it will be read. It also runs a simulation mode with no API calls at all, and it can prove a top-K: any token outside the top 20 has a logprob at or below the smallest one shown, which bounds the whole unseen subtree and lets the frontier be cut off without exploring it.

The store

The store is server.py. It holds every record from every source file — the root history, all sweeps, the builder's output — and answers one question the whole set used to answer four different ways: do we already have this call?

Both generators ask it as the last stop before spending. The order is: this browser's own history, then the imported sweep cache, then the store, and only then the API. In the builder that turned seven expansions costing seven calls into seven expansions costing nothing.

It can be switched off — a chip in the token browser, a select in the builder — and it switches itself off in effect whenever it cannot be reached. Either way the program falls back to exactly what it did before: call the API. The lists, on the other hand, are computed by the store, so with it stopped they will not load at all.

Rankings are served live rather than read from exported files. An export goes stale silently: the one that fed this viewer had been built from 391 records while 8492 existed, and contained no sweep data at all.
